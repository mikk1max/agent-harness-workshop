Harness agentowy

Wiele agentów, jeden plan — i scout, który pilnuje progresji

Jeden agent się kończy

Sesja agenta jest krótka i śmiertelna: kontekst rośnie, budżet iteracji i tokenów się wyczerpuje.

Wielogodzinna praca nie mieści się w jednej sesji. I nie ma się mieścić — to nie błąd, to własność.

Stan żyje poza modelem

goal.md        cel całości
plan.md        kroki z kryteriami "zrobione"
episodes/      kronika kolejnych epizodów
  *-signal.json   pliki sygnałów agentów danego epizodu

Sesje są jednorazowe. Wszystko, co ma przetrwać, mieszka w plikach. Model zapomina — pliki nie.

Harness

(implementer → release manager → detektyw) → scout →
(implementer → release manager → detektyw) → scout → …

Epizod agentów, werdykt detektywa, potem deterministyczne przejście do następnego stanu planu. I tak aż plan zostanie ukończony — albo detektyw wyda werdykt walled.

goal.md i plan.md

Cel — jedna strona, nikt go nie edytuje. Plan — kroki z checkboxami; każdy krok ma kryterium sprawdzalne poleceniem:

- [ ] 2. zapis do pliku — `node test.js` kończy się kodem wyjścia 0

Kryterium "zrobione" to nie "działa ładnie". To polecenie i kod wyjścia — i jest zamrożone: implementer nie edytuje ani jego treści, ani testów, które je realizują.

Jeśli agent może zmienić test zamiast implementacji — zmieni test.

Role zamiast supermózgu

Implementer — pisze kod dla bieżącego kroku.
Release manager — dopuszcza do wydania: sam uruchamia kryterium; drobne usterki poprawia, większe opisuje w pliku sygnału.
Detektyw — szuka tropów; diagnozuje, nie naprawia.

Każda rola to claude -p z innym promptem. Własnej pętli z pierwszego warsztatu tu nie używamy — Claude Code jest dojrzalszą realizacją tej samej idei.

Sygnały — rozmowa przez pliki

{
  "agent": "release-manager",
  "episode": 3,
  "step": "2-zapis-do-pliku",
  "status": "fail",
  "summary": "Wczytanie pustej listy wywala program.",
  "artifacts": ["episodes/episode-3/test-output.txt"]
}

Każdy epizod ma własny komplet sygnałów w swoim katalogu. Agenci nie dzielą kontekstu — co ma wiedzieć następny, musi zostać zapisane.

Release manager nie wierzy implementerowi

Implementer mówi "zrobione". Release manager nie czyta zapewnień — sam uruchamia kryterium. Literówkę poprawi sam, wszystko większe opisuje w swoim pliku sygnału.

Jego plik sygnału — nie zapewnienia implementera — to główny dowód dla detektywa. Kto pisał, ten nie dopuszcza do wydania.

Scout — kod, nie model

werdykt: advance   → odhacz krok, bierz następny
werdykt: retry     → powtórka + diagnoza w prompcie
werdykt: walled    → ściana — czekaj na człowieka
brak sygnału       → powtórz sesję z dopiskiem
plan odhaczony     → koniec

Scout nie ocenia pracy — wykonuje werdykt detektywa. Zero tokenów, zero kreatywności. Dlatego harness daje się debugować.

Brak sygnału to nie werdykt

Brak pliku niczego nie rozstrzyga i nie zatrzymuje harnessu. Scout powtarza tę samą sesję — z dopiskiem, że poprzednia próba nie zostawiła pliku sygnału.

Harness projektujesz od strony awarii, nie sukcesu.

Detektyw bada każdy epizod — i wydaje werdykt

Po porażce pisze diagnozę. Po sukcesie sprawdza, czy wynik jest wiarygodny: test przeszedł zbyt łatwo, kod obchodzi kryterium, dług techniczny został zamieciony pod dywan.

Werdykt: advance / retry / walled — ściana znaczy: bez decyzji człowieka się nie ruszy. Tropy trafiają do następnego epizodu — kolejne epizody korzystają ze stanu zapisanego w plikach, nie z pamięci modelu.

Twarde limity — na dwóch poziomach

W sesji agenta: --max-turns przekazany do claude -p.
W harnessie: limit epizodów — ale tylko jako bezpiecznik.

O zatrzymaniu pracy decyduje werdykt walled, nie licznik. Bezpiecznik jest na wypadek, gdyby wszystko inne zawiodło — bo nikogo nie ma przy klawiaturze, żeby przerwać.

Co dziś zbudujesz

goal.md + plan.md
      │
      ▼
epizod: implementer → release manager → detektyw
      │            (sygnały *.json)
      ▼
scout (kod) ── odhacza / powtarza / stop
      │
      ▼
episodes/episode-N/ … aż plan zostanie ukończony

Uruchamiasz raz; dalej pracuje harness. Wracasz do procesu dopiero przy statusie walled.

Harness pracuje obok ludzi

Uruchamiasz go i wracasz do własnej, równoległej pracy (developer side tracks).

Harness wymaga twojej interwencji tylko przy werdykcie walled albo po ukończeniu planu.

No dobra, to programujemy!

node harness.js plan.md

Pomysły na harness — serwisy (1/2)

Strażnik repo — pilnuje zależności i bezpieczeństwa: backlog bierze z npm outdated i npm audit, sam dobudowuje sobie checkery (skan sekretów, wersje obrazów). Patch podnosi kodem; przy majorze robi research i otwiera MR.

Devops z healerem — monitor deterministycznie sprawdza dysk, procesy i usługi; healer naprawia w granicach mandatu z goal.md (cache może skasować, danych nie tknie); watchdog co N obiegów prowadzi śledztwo, czemu problem wraca.

Evergreen research — żywy raport na zadany temat: budowniczy tworzy scrapery źródeł (raz zbudowane, pobierają dane bez wywołań modelu), analityk co N obiegów ocenia, czy pojawiło się coś ważnego — i pisze na Telegrama.

Pomysły na harness — serwisy (2/2)

Spinacz komunikacji — czyta maile, Slacka, transkrypcje spotkań, Jirę i support; robi podsumowania i krzyżowo sprawdza spójność: obietnica ze spotkania ma ticket, problem z maila ma odpowiedź, nic się nie zgubiło.

Analityk biznesowy — schodzi po backlogu issues i pod każdy feature robi deep research: kontekst rynkowy, ryzyka, pytania do klienta. Analiza czeka gotowa, zanim ktokolwiek weźmie ticket.

Labelowanie danych — labeluje partiami; gdy trafi na dane, które nie mieszczą się w typologii, rozbudowuje ontologię, poprawia stare labelki i jedzie dalej.

Pomysły na harness — pętle badawcze (1/2)

Turniej — wspólny deep research składa dossier, potem N niezależnych sesji rozwiązuje to samo zadanie (feature, artykuł, architektura) — żadna nie zna cudzych planów. Bramki deterministyczne odsiewają, sędzia porównuje według kryteriów oceny z goal.md, a synteza bierze zwycięzcę i kradnie najlepsze pomysły przegranych.

Optymalizator przestrzeni projektowej — przestrzenią jest parametryczny CAD (code-CAD) albo features modelu ML. Agent proponuje kandydata, symulacja albo metryka ocenia go kodem, najlepszy zostaje punktem wyjścia następnego epizodu — i tak aż metryka przestanie się poprawiać przez kilka epizodów.

Pomysły na harness — pętle badawcze (2/2)

Model rynku — model rośnie wzdłuż łańcucha spięć rynkowych: kredyty → mieszkania → materiały budowlane → tartaki | kopalnie. Research proponuje kolejne ogniwo i dokłada szeregi danych, kod liczy korelacje na roku testowym (2025, YTD) — hipoteza zostaje tylko, jeśli dane jej bronią. Każde ogniwo podsuwa następne: backlog generuje się sam.

Dekonstrukcja storytellingu — książka po książce z kanonu: research rozbiera każdą na strukturę historii, ontologia wzorców fabularnych rośnie i jest poprawiana wstecz. Książka, która nie pasuje do żadnego wzorca, to walled — człowiek decyduje, czy to nowy wzorzec.

Pomysły na agenty — nazwy się liczą

budowniczy   inspektor   healer      sygnalista
detektyw     sędzia      sceptyk     syntezator
analityk     redaktor    kronikarz   negocjator

Rola to prompt, a nazwa robi jego połowę: detektyw szuka tropów, inspektor nie wierzy na słowo, healer nie wychodzi poza mandat.

Kapelusze de Bono jako gotowa paleta — sceptyk "to się nie uda" zamienia wątpliwości w ograniczenia rozwiązania.

Deterministyczne integracje — macierz

czytają świat      ściąganie z API · scraper · transkrypcja
    
mierzą             checker · walidator · diff snapshotów ·
                   symulacja/metryka · backtest/korelacja

piszą do świata    MR · Telegram · mail · raport — zawsze przez outbox

Agent buduje je raz — potem kręcą się bez modelu. Harness rośnie o narzędzia, nie o tokeny.

Dzieje się coś dziwnego? Trzeba zareagować? Jest coś nowego wymagającego rozkminy? → odpalamy agenta albo informujemy usera.

Szkielet zawsze ten sam: scout, epizody, sygnały. Wymyśl własny.

Metakognicja — zrozumienie rozumowania

Im lepiej rozumiesz własny proces rozumowania, tym łatwiej potrafisz rozłożyć go na komponenty i zbudować podobny proces w systemie agentowym.

świat       z jakiego modelu rzeczywistości korzystam?
zadanie     jak rozpoznaję cel i ograniczenia?
strategie   jak wybieram sposób rozwiązania?
niewiedza   skąd wiem, czego nie wiem?
inni        jak wiedza o innych zmienia moje rozumowanie?
kontrola    kiedy kończę, sprawdzam, zmieniam strategię albo deleguję?

Najpierw obserwujesz własne „rozkminy”, potem eksternalizujesz je jako architekturę agenta.
